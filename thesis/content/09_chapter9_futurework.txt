CHAPTER 9: LESSONS LEARNT AND FUTURE WORK

9.1 Lessons Learnt

A score with no memory reproduces whatever bias its single input has. The first version of the selection pipeline sorted candidate clips by similarity-to-summary and took them in order until the time budget ran out. Measured directly on this project's own completed jobs rather than suspected from reading the code, this put as much as 80-100% of a job's selected material in the first half of the source video, and in one case the pipeline's own three separate places that each added padding to the running total (the selector, the merge-formatting step, and a later "fit to duration" step) compounded into a budget overshoot of 352% on one job and an undershoot to 8% of the requested budget on another. The fix was not a bigger or better similarity score; it was making the gain from selecting a segment explicitly diminish as similar material was already selected (submodularity), and separately rewarding under-represented regions of the timeline as a concave function rather than a flat bonus. The lesson generalised: a score intended to rank many similar candidates needs a term for "have I already picked something like this", or its ranking will reproduce whatever structural bias its underlying signal has — in this case, that an early segment introducing a topic looks similar to almost any summary of that topic.

A length check is not a quality check. The original summarisation step opened with a single guard: if the selected text was already shorter than the target word count, skip the compression model entirely. This conflated "is this long enough to need compressing" with "is this good enough to ship", and on one real job it meant the text summarisation model (distilBART) ran for one source video and was silently skipped for another, functionally identical, source — purely because of which side of a word-count threshold the two landed on. The version that was skipped carried visible connective-word artifacts ("...Additionally, To reach four and five we need...") stitched in by an earlier narrative-assembly step, landing mid-sentence because the preceding clause had no terminal punctuation on an auto-captioned source. The fix was to separate compression (a length question) from coherence (a text-quality question) into two independent checks, so that a narrative which is short enough to skip compression can still be routed through a lighter coherence-repair pass if it needs one. The general lesson: a cheap proxy check ("is it short enough already") is not a substitute for the property actually being protected ("does it read correctly"), and a pipeline that conflates the two will silently under-serve exactly the inputs that happen to pass the proxy check for the wrong reason.

An absolute similarity threshold is not portable across embedding models. Concept deduplication merges near-duplicate concept names using a cosine-similarity threshold on their sentence embeddings. A threshold tuned against the originally-used all-MiniLM-L6-v2 model, whose embeddings spread unrelated short strings across a comparatively narrow 0.2-0.4 range, was carried over unchanged when the project migrated to BAAI/bge-base-en-v1.5, whose embeddings pack unrelated strings noticeably closer together, above roughly 0.7. Applied unchanged, that threshold merged every concept extracted from a real 25-minute video into a single cluster labelled "work" — a silent, total loss of concept granularity that would not have been obvious without directly inspecting the output. The fix made the operating threshold self-calibrating: the higher of a fixed floor and the 95th percentile of the similarities actually observed in that video's own concept set, rather than one constant assumed to transfer between encoders. The lesson: any threshold tuned against one embedding model's geometry is a property of that model, not of the task, and must be revisited — ideally made self-calibrating — whenever the underlying model changes.

A fixed redundancy baseline measures the wrong thing for a single-topic source. An early version of the redundancy metric scored similarity between two selected passages against a fixed threshold, and reported 59% redundancy for a selection that a direct listen confirmed was in fact more diverse than the source material it was drawn from. The problem was definitional: two passages of one podcast, in one speaker's voice, on one subject, are simply going to be more similar to each other than two passages of unrelated text would be, and how much more similar depends on the embedding model. The fix was to measure redundancy relative to that specific video's own baseline — the mean nearest-neighbour similarity across all of its candidate segments — so the metric answers the question actually being asked ("are these picks more alike than an arbitrary handful from this same video would be") rather than an absolute, context-free one. The same honesty extended to evaluation: a later, more rigorous ablation study found that this redundancy penalty, once measured this way on genuinely held-out data, did not produce a measurable reduction in pairwise similarity relative to not having it at all — a result that was reported plainly rather than omitted, because a metric redesigned to ask the right question can still reveal that the mechanism it is checking does not yet do what it was built to do.

Concurrency limits for a local model server are a correctness fix, not a throughput one. Firing many concurrent requests at a locally-hosted Ollama instance for concept extraction did not speed anything up, because Ollama serialises generation internally; the effect was that most requests sat in an internal queue burning their own per-request timeout while waiting rather than generating, so they then failed with a timeout error against a server that was, from the outside, perfectly healthy. Bounding concurrency to two in-flight requests fixed this, and a matching design choice — setting the HTTP client's own timeout below the asyncio-level timeout wrapping it — was necessary because asyncio's timeout cannot actually kill a background OS thread already running a blocking call, so the inner timeout has to fire first or the outer one does nothing but abandon a request that keeps running and keeps holding a server slot.

9.2 Future Work

Speaker diarisation as a segmentation signal. The semantic segmenter currently derives topic boundaries purely from sentence-embedding similarity; a speaker change is a strong, currently unused boundary signal, particularly for interview and panel-discussion content where a new speaker very often also means a new sub-topic. Integrating a diarisation model and feeding speaker-change points into the boundary-detection logic alongside the existing similarity signal is the most immediately promising unimplemented improvement to segmentation quality.

Re-enabling visual signal by default for visually-driven content. Visual scoring (via CLIP and the keyframe extractor) is implemented, tested, and currently disabled by default in favour of a lighter audio-energy scorer tuned for single-speaker podcast and lecture content, which is what the project's own evaluation corpus is predominantly composed of. Extending the evaluation to visually-driven content (demonstrations, product reviews, visual tutorials) and re-enabling and re-tuning the visual signal specifically for that content type is a natural next step rather than a rewrite, since the code path already exists.

Human evaluation of narrative ordering and overall summary quality. The project's own held-out ablation study explicitly flagged that its narrative-reordering component's benefit to a human reader, and the system's semantic-efficacy metric more generally, remain marked "pending human annotation" (evaluation/human_annotation_sheet.md and human_rating_protocol.md already define the protocol for this). Running that already-designed human evaluation to completion is the clearest remaining gap between what has been measured and what the system's design is actually trying to achieve.

Enabling LLM-backed concept extraction on appropriate hardware. The Ollama-backed concept-extraction path is complete and covered by the same test suite as the TF-IDF fallback, but is disabled by default purely because of a measured CPU-latency constraint on the project's development hardware. Deploying the platform on GPU-class hardware (or a smaller/faster local model) and re-enabling this path would very likely improve concept quality (the LLM path extracts named, explained concepts with supporting reasoning text, versus the fallback's bare keyphrases) without requiring new engineering work, only a different deployment environment.

Horizontal scaling of the output workers. The durable, lease-based task-claiming design in output_task_queue.py was built specifically to be correct under multiple concurrent worker instances of the same type, even though the current deployment runs exactly one video worker and one text worker. Actually running multiple replicas of each behind the existing lease mechanism, rather than a single instance of each, would let the platform's rendering throughput scale with deployed hardware rather than being bounded by one worker process per output type.

A CI/CD pipeline. The project's 548-test suite currently runs manually. Wiring pytest into a GitHub Actions workflow on every pull request, and extending it to build and smoke-test the Docker images described in Chapter 4's deployment diagram, would catch a regression before it reaches a deployed environment rather than depending on a developer remembering to run the suite locally.

A native mobile application. The current platform is web-only. Given how much of the user experience already revolves around a job completing in the background while the user is doing something else, a companion mobile app (or an installable PWA as a lighter first step) that can notify a user when a job reaches video_ready or completed is a natural extension of the existing architecture rather than a new one.
