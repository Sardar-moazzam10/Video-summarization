CHAPTER 4: SYSTEM DESIGN

The diagrams referenced in this chapter are inserted as figures alongside the explanatory text below. Each subsection describes what the corresponding diagram shows and why it is structured the way it is, grounded in the actual modules and classes present in the codebase.

Architecture Diagram

The architecture diagram shows VidFusion as a layered system: a React/Tailwind single-page frontend, a FastAPI REST API, a durable MongoDB-backed task queue, two independent background workers, and a distinct layer of locally-hosted AI models the pipeline depends on. The frontend never talks to MongoDB, ffmpeg, or the AI models directly — every request goes through the FastAPI layer, which is the only component holding database credentials and model configuration. Inside the backend, the diagram separates Routers (thin HTTP-to-service wiring, one per feature area: auth, merge, transcript, search, chat, rights, youtube), the Merge Pipeline (the core orchestration that runs transcription through to evidence-manifest publication), and the Service Layer (semantic segmentation, concept extraction, coverage selection, summarisation policy, fusion, rights, and acquisition-observability logic). A distinct pair of boxes represents the Video Worker and Text Worker, drawn separately from the API process because — when SEPARATE_OUTPUT_WORKERS_ENABLED is set, which is how the project's own docker-compose.yml runs it — they are genuinely separate OS processes (and, in the Docker topology, separate containers) that poll the durable output-task queue independently, rather than threads inside the API process. The diagram is structured this way specifically because the lease-based claiming logic in output_task_queue.py is written to be correct under multiple concurrent worker instances, which the current one-worker-per-type deployment does not strictly require but is deliberately built to support.

Entity Relationship Diagram (ERD)

The ERD is built directly from the collections the backend actually persists to: users, history, jobs, transcripts, source_rights, acquisition (the decisions/events/manifests of the shadow-observability system), and output_tasks. A user document is the root entity every other collection references by user_id. The jobs collection is the largest and most central: each MergeJob document embeds its own results (segments, concepts, rich_output, fusion_metadata, selection_metrics) directly on the document rather than splitting them into child collections, because they are always read and written as a unit with their parent job and never queried independently of it — the same "document-shaped, not relational" reasoning that motivated choosing MongoDB in the first place (Chapter 6). The output_tasks collection has a one-to-many relationship from jobs (one job can have up to two durable tasks, one per output type) and is the one collection with its own independent lifecycle fields (lease, worker ownership, attempts) distinct from the parent job's own status, reflecting that a task's claim/lease state is worker-queue bookkeeping, not job-level business state. source_rights has a many-to-one relationship into users (many rights records per user, one per source video they have asserted a basis for) and is referenced from a job's frozen rights_snapshot by value, not by live reference, since a snapshot must not change retroactively if the user's recorded rights basis changes later.

DFD Level 0 (Context Diagram)

The Level 0 diagram treats the whole VidFusion backend as a single process and shows its data flows to and from four external entities: the User (via the browser), the Database (MongoDB), the Video Platform (YouTube, reached for source video/caption acquisition), and the AI Model Layer (collectively, since at this level which specific model — Whisper, SBERT, distilBART, or Ollama — handles a given call is not yet relevant). The User submits video selections and a target duration and receives job-progress updates and a finished summary; the system reads and writes user accounts, job state, and transcripts to the Database; it fetches source video, audio, and captions from the Video Platform; and it sends transcript text to, and receives transcriptions, embeddings, summaries, and extracted concepts from, the AI Model Layer.

DFD Level 1

The Level 1 diagram decomposes the single process from Level 0 into its major functional processes: Authentication, Merge Job Creation, Semantic Selection (segmentation, concept extraction, coverage-budgeted selection), Output Generation (video rendering, text summarisation), Search/Chat, and Rights Governance, each shown with its own data flows into and out of the relevant data stores. Output Generation is drawn as consuming a single, fixed input — the evidence manifest produced by Semantic Selection — rather than reading the raw transcript or re-running selection itself, which mirrors the actual code path: once a manifest is published, the video and text workers are deliberately prevented from seeing anything upstream of it, so neither output's generation logic can silently diverge from what was actually selected.

Class Diagram

The class diagram combines the persistent data model with the Service-layer classes that create or mutate it. MergeJob sits at the centre, referenced by output_tasks (a 1-to-N composition, since a task's lifecycle is entirely owned by its parent job) and User (a many-to-one "belongs to" association). MergeJob contains, as embedded value objects rather than separate referenced classes (UML composition, the filled-diamond end), its own ConceptInfo list, VideoSegment list, RichOutput, and FusionMetadata, mirroring that these are read and written as part of the job document itself. SourceRightsRecord is drawn referencing User by id rather than being embedded in it, since a user accumulates many rights records over time and they are queried independently (by source id) rather than always loaded with the user. Around this data model, the Service classes are shown with dashed dependency arrows: SemanticSegmenter and ConceptExtractor both produce input consumed by CoverageSelector; CoverageSelector's output is consumed independently by both VideoService (rendering) and SummarizationPolicy/FusionEngine (text), reflecting the manifest hand-off described above; RightsService is shown depending on MergeJob only to read its selected segments and source durations when building a reuse report, never to mutate job state itself.

Activity Diagram

The activity diagram traces the Create Merge Job use case as a swimlane flow between the User, the API, and the two Background Workers. The User's lane is short — submit sources and a duration, later view the result — while the pipeline's lane carries the bulk of the activity: transcribe, segment semantically, extract concepts, select segments under budget, then a fork into two parallel branches once the evidence manifest is published — one branch (the Video Worker) rendering the highlight reel with ffmpeg, the other (the Text Worker) running the summarisation policy and producing the structured written output — which join only in the sense that both write back to the same job document, each updating only its own component's status field. A decision diamond appears after the concept-extraction step, representing the Ollama-available/unavailable branch that determines whether concepts come from the LLM path or the TF-IDF fallback, and another after segmentation, representing the SBERT-available/unavailable branch that determines whether semantic boundaries or duration-only boundaries are used.

Sequence Diagram

The sequence diagram details the Create Merge Job use case through to the video_ready checkpoint, chosen because it best demonstrates the system's two-worker, manifest-handoff design. It shows the frontend calling POST /api/v1/merge, the router validating duration feasibility and creating the MergeJob document, and returning a job_id immediately rather than blocking on the pipeline. A second, independent timeline then shows the core pipeline running segmentation, concept extraction, and selection, and publishing the evidence manifest; from that point, two further independent lifelines show the Video Worker and Text Worker each separately claiming a durable task referencing that manifest, each updating only its own component's state, and the Video Worker's completion being what flips the job into the non-terminal video_ready status while the Text Worker is still running.

Collaboration Diagram

The collaboration diagram represents the same Create Merge Job use case as the sequence diagram but organised around the objects and their message links. The request chain runs across the top — User to the React SPA, to the Merge router, to the job-creation logic — exactly as in the sequence diagram, but the collaboration view's real value is in what radiates outward from CoverageSelector: it receives segments from SemanticSegmenter and concepts from ConceptExtractor (messages 4 and 5), and its own output is a single evidence manifest consumed independently by VideoWorker and TextWorker (messages 6 and 7), making explicit that CoverageSelector is the single point where segmentation and concept signals are combined, and that neither output worker is ever reachable directly from the router or from each other.

State Transition Diagram

The state transition diagram models the lifecycle of a MergeJob's status field, which is the clearest explicit state machine in the system: pending -> transcribing -> analyzing -> fusing -> summarizing -> enriching -> generating_video, with a non-terminal video_ready checkpoint reachable once the highlight reel specifically is finished but before the written summary has, from which the job still proceeds on to one of the terminal states completed, partial_success (one output component failed, the other succeeded), or error. The diagram also shows cancelled as a terminal state reachable from any non-terminal status. This diagram is included because the reliability story in Chapter 2's non-functional requirements is a claim about this state machine behaving correctly under worker crashes and restarts — which is exactly what the lease/heartbeat fields on the underlying output task (claimed_at, lease_expires_at, worker ownership) exist to guarantee, recovered on worker startup by recover_expired_output_tasks.

Component Diagram

The component diagram groups the backend into Frontend, Routers, Pipeline/Services, and Infrastructure layers, connected through explicit provided and required interfaces rather than plain arrows. The Frontend depends on a single RouterAPI socket over HTTP/REST; each router then exposes its own provided interface (MergeAPI, AuthAPI, SearchAPI, ChatAPI, RightsAPI) and requires the matching service interface. MergeAPI requires both a SelectionPipelineAPI (segmentation through evidence-manifest publication) and an OutputTaskQueueAPI (for status/retry operations), while ChatAPI requires both a VectorSearchAPI (FAISS) and, optionally, an LLMProviderAPI (Ollama) — drawn with a dashed optional-dependency arrow specifically because the chat use case is designed to function with that dependency entirely absent. On the Infrastructure side, VideoWorker depends on MediaProcessingAPI (ffmpeg) and PersistenceAPI (MongoDB); TextWorker depends on SummarizationModelAPI (the local HuggingFace models) and PersistenceAPI; both depend on OutputTaskQueueAPI to claim and complete their tasks.

Deployment Diagram

The deployment diagram shows the project's actual docker-compose.yml topology: an app container (the FastAPI API, exposed on port 8000), a text-worker container and a video-worker container (each built from the same image but started with a different module entry point), and a mongo container (MongoDB 7), all sharing two named Docker volumes — audio_cache (the local scratch and highlight-video cache every container needs read/write access to) and faiss_index (the shared vector search index) — so that whichever container produces or needs a given file sees the same filesystem state regardless of which container actually writes it. The app container is the only one exposed outside the compose network; the two workers and MongoDB are reached only from inside it. This topology is the project's reproducible, self-contained deployment target, independent of any specific cloud platform.
